1. Square admin endpoint is still not safely locked

What is happening

There is a backend route that can connect, disconnect, or sync Square for a gym. Right now the dangerous actions are still reachable without enough proof that the caller is the real owner of that gym.

Plain English

Imagine the gym's payment system has a control panel. The app needs to check a person's ID before letting them push the big buttons. Right now, some big buttons can still be reached without a strong enough ID check.

Solution

Require a signed-in user token for connect_url, disconnect, and sync. Then check that the signed-in profile is an owner for the exact program_id. Keep read-only status and public config open if needed, because those do not change money settings.

Proof Needed

Unauthenticated disconnect returns 401. An owner from another gym cannot disconnect MCA. A legitimate MCA owner can still connect and sync Square.

2. Roster writes can still be local-only

What is happening

The roster screen now shows better error messages and refreshes after changes, but its add, edit, and remove paths still call window.HZdb.from('athletes'). That path is localStorage-backed unless it is explicitly converted to the live Supabase write pattern.

Plain English

The app may write the new athlete on a sticky note in the browser instead of saving it in the real database. When the app reloads from the real database, the sticky note gets thrown away.

Solution

When live mode is active, write roster changes directly to Supabase with the logged-in user's program scope. After Supabase confirms the save, update the local mirror and refresh the screen.

Proof Needed

Add an athlete in production, reload the app, and confirm that athlete still appears from another browser or device.

3. Announcement writes can still be local-only

What is happening

Announcements are read from live Supabase, but create, edit, and delete still go through window.HZdb.from('announcements') in the owner screen.

Plain English

A gym owner can type an announcement and think it was posted, but families may never see it because it only saved inside the owner's browser.

Solution

Use the same dual-write/live-first pattern as the working program offerings and parent-link flows: save to Supabase first, reconcile local data second, then refresh.

Proof Needed

Post a gym announcement as owner and verify it appears in a parent account on another device.

4. First-row fallback logic remains

What is happening

The quality monitor still found five places where production screens use the first item in an array, such as the first program, team, or athlete, instead of an explicit viewer scope.

Plain English

The app sometimes says, "I will just use the first gym or first athlete in the list." That is okay only by luck. If another gym or profile appears first, the app can show the wrong data.

Solution

Replace every first-row shortcut with scoped selectors: use the signed-in profile's program_id, the parent's linked athlete IDs, or a clear empty state when the app cannot determine scope.

Proof Needed

Seed or simulate a second program and confirm each owner, parent, coach, and athlete screen only shows the data they should see.
